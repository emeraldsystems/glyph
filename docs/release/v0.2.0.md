# Glyph v0.2.0

Released from `master` at GLYPH-90. Previous published state was v0.1.0
(untagged), effectively GLYPH-88.

This release exists for one change: **`glyph build --release` now actually
optimizes.** Until GLYPH-90, `--release` only selected an output directory
while object emission always ran at O0, so a "release" build carried none of
LLVM's optimization. That made the flag misleading and made Glyph unusable
for anything with a real-time budget.

## What changed

- **Release builds run LLVM's `default<O2>` pipeline** plus optimized
  machine-code emission, on a cloned module so the debug API is preserved.
  Plain `glyph build` still uses O0.
- **Floating-point semantics are unchanged.** O2 is enabled *without* fast
  math and without multiply/add fusion, so release and debug builds produce
  identical arithmetic. This was a design requirement, not an accident: the
  flagship consumer pins a content hash of its audio output, and a release
  build that reassociated float operations would have broken it silently.
- The CLI reports the optimization level it used.

## Why it is a minor bump rather than a patch

No language or library surface changed, and nothing that compiled under
v0.1.0 fails under v0.2.0. But the performance profile of every release
build changes by roughly an order of magnitude, which is not a patch-level
difference for anyone depending on it. Pre-1.0, that is a minor bump.

## Validation

From the change itself:

- `cargo test --features codegen`: 952 passed.
- A 20.48 M-iteration indexed float update loop runs **13× faster** with
  **identical output**.
- `crates/glyph-cli/tests/release_optimization.rs` (403 lines, new) asserts
  actual machine-code reduction, `Vec`/`String` ownership under O2, nested
  aggregate returns, and rounding-sensitive `f32`/`f64` results.

From the downstream consumer, which is the evidence that matters most for a
codegen change — an optimizer bug would show up as altered output, not as a
failed assertion:

- **GlyphAudio's full suite: 215 passed, 0 failed, 1 skipped** (the skipped
  one needs a real audio device).
- **Its pinned canonical render hash did not move.** GlyphAudio renders a
  fixed four-bar song and pins an FNV-1a content hash of the audio
  (`0x9baf8ecdb86db9b7`). That hash is byte-level evidence that O2 changed
  no arithmetic anywhere in a non-trivial DSP program: oscillators, filters,
  envelopes, a delay line and a mixer. It is unchanged under this release.
- A separate Glyph program in that project (`analysis/`, an FFT-based audio
  measurement tool) builds and passes its own self-test under O2, including
  a transform whose correctness is asserted against hand-computed values.

## Identifying this build

`crates/glyph-cli/build.rs` derives the version string from
`git describe --tags --exact-match`, falling back to the short commit hash.
Because this release is tagged, a binary built from the tag reports:

```
$ glyph --version
glyph 0.2.0 (v0.2.0)
```

A binary built from a detached source archive with no `.git` directory
reports a bare `glyph 0.2.0` and cannot be identified by commit. Build from
a real checkout when the version string needs to be meaningful — downstream
toolchain gates read it.

## Installing

```sh
just build && just install
```

## Note on the branch name

The work was done on `glyphaudio-release-optimization`, named for the
project that needed it. The change itself is not audio-specific: it is the
optimizer pipeline for every release build in the language. It is on
`master` as of this release.
